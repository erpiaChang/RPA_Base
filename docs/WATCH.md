# 시간대 반복 조회 — 기획 (10-06, 만들기 전)

**기획만 했다. 코드는 없다.** 업체 화면 조사(UIA)가 끝나기 전에는 만들지 않는다 (CLAUDE.md).
10절의 사용자 결정(10-06)을 반영했다.

## 1. 무엇을 하나

외부 시스템이 데이터를 **한꺼번에 넘기기도 하지만 하나씩 넘기기도 해서**, 정해진 시간대 동안
화면 하나를 N분마다 조회하고 처리할 건이 있으면 저장(→ 다음 단계로 넘김)해야 하는 경우가 있다.

```
예: 12:00 ~ 13:00, 5분마다
12:00 조회 → 0건 → 기다림
12:05 조회 → 3건 → 저장(팝업 [예]) → 기다림
...
13:00 조회 → 끝, 요약
```

- **실행은 1번이다.** 시작·로그인 한 번, 화면 하나에서 일한다. 사용량(요금 기준 횟수)도 1 (6절).
- 조회·저장 횟수는 그 실행의 **상세**로만 남는다 (7절).
- 앞으로 다른 업체에도 필요할 수 있는 형태라, 화면을 모르는 **엔진**과 화면을 아는 **작업**으로 나눈다.

## 2. 구조 — 엔진과 화면 작업

| 조각 | 하는 일 | 어디에 |
| --- | --- | --- |
| 엔진 (가칭 `orchestrator/watch.py`) | 시간대·간격 계산, 다음 조회까지 기다리기, 중단·일시정지, 잠긴 화면, ERPia 살아 있나, 연속 실패 상한, 기록 | **원본(공용)** — 이 ERPia RPA 의 화면(예: 자동수집)에도 쓴다 (사용자 결정 10-06) |
| 화면 작업 (`WatchTask`) | 그 화면을 열고, 조회해 건수를 읽고, 저장한다 | 업체 전용 (`docs/CUSTOMERS.md` 의 업체 파일) |

화면 작업 계약 — 엔진은 이것만 부른다.

| 메서드 | 뜻 |
| --- | --- |
| `name` | 화면 이름 (로그·표에 나온다) |
| `prepare()` | 화면을 연다. 처음 한 번, 그리고 다시 로그인한 뒤 |
| `count() -> int` | [조회] 를 누르고 **처리할 건수**를 읽는다 (예: 단계 상자의 건수, 그리드 행 수) |
| `process() -> Saved` | 체크 → 저장/화살표 → 팝업 [예] 까지. 넘긴 건수와 메모를 돌려준다. 넘어가지 않는 [확인] 팝업이면 예외 대신 `Saved(0, 사유)` |

- **한 실행에 반복 대상은 하나다** (5절, 사용자 결정). 화면 여러 개를 같은 시간대에 돌려야 하면 시간대를 나눠 예약한다.
- 화면 작업은 저장 뒤 팝업 문구의 건수와 체크한 건수를 대조하고 [예] 를 누른다 (다르면 '확인할 것').

## 3. 한 번의 실행

```
예약 시각(시간대 시작) 또는 [실행] → 앞에 필요한 단계(ERPia 실행·로그인 등) → prepare()
반복 (끝 시각까지, 끝 시각 포함):
  화면이 잠겼다          → 이번 차례만 건너뛴다 (기록)
  ERPia 창·로그인이 없다 → 다시 로그인 한 번 → prepare()   (안 되면 끝, '확인할 것')
  count() → 0 이면 '없음' / >0 이면 process()
  다음 조회 시각까지 기다린다 (중단·일시정지에 반응)
끝 → 요약 한 줄
```

- **조회 시각은 시작 시각 기준 격자다** (12:00, 12:05, 12:10 …). "끝난 뒤 5분" 이 아니다 — 저장이 길어져 다음 칸을 넘기면 그 칸은 건너뛰고 다음 칸에 한다 (밀린 것을 몰아서 하지 않는다).

## 4. 규칙

**확정** (사용자 10-06): 간격·최대 시간·끝 시각 포함·늦은 시작. 나머지 줄은 제안.

| 항목 | 규칙 | 이유 |
| --- | --- | --- |
| 간격 | **1 ~ 60분** (확정) | 1분 미만은 ERPia 에 부담. 지금 간격 예약의 10분 하한과는 별개다 |
| 최대 반복 시간 | **1시간** (확정, 우선) — 시작~끝이 60분을 넘는 시간대는 받지 않는다 | 길어질수록 세션 만료·화면 잠김 위험이 커진다. 늘리는 것은 실측 뒤 |
| 끝 시각 | **포함 — 끝 시각에 한 번 더 한다** (확정). 12:00~13:00 / 5분이면 13번 | "13시까지 진행" |
| 끝 시각에 저장 중 | 끝까지 마친다 | 저장을 중간에 끊지 않는다 |
| 연속 실패 | 같은 화면에서 3번 연달아 실패하면 그 화면만 멈추고 '확인할 것' | 무제한 재시도 금지 (CLAUDE.md) |
| 넘어가지 않는 [확인] 팝업 | 그 차례는 '확인할 것', 다음 차례는 계속. 같은 문구는 한 번만 알린다 | 예: "검토가 필요한 전표" |
| 늦게 시작 (PC 잠자기 등) | **끝 시각 전이면 지금부터 들어간다** (확정). 지금 예약의 "10분 넘게 놓치면 건너뜀" 의 예외 | 남은 시간대도 쓸모가 있다 |
| 시작 때 화면이 잠겨 있다 | 끝 시각 전까지 1분마다 다시 보고, 풀리면 들어간다 (늦은 시작과 같은 원칙) | 위와 같다 |
| 실행 전체 상한 | 끝 시각 + 30분 | 지금 흐름 전체 상한이 없다. 오래 도는 실행이라 따로 둔다 |
| [중단]·웹 [RPA 종료] | 다음 대기 지점에서 끝, 결과 '중단' | 지금과 같다 |
| 창·오버레이 [일시정지] | 대기 중에도 멈춘다. 풀렸을 때 다음 조회 시각이 지났으면 바로 조회 | |
| 웹 [일시정지] | 지금처럼 **예약만** 멈춘다 (도는 실행은 그대로) | 지금 규칙 (`docs/SETTINGS.md` 원격 표) |

## 5. 반복 대상 고르기 — 화면 하나만 (사용자 결정 10-06)

**반복은 "특정 화면의 특정 구간" 하나에만 건다.** 기능(모듈)보다 잘다 — 예: 메일·사이트 기능 안의 '엑셀 다운로드', 주문수집·매출처리 기능 안의 '자동수집'.

| 반복 대상 (예) | 함께 고를 수 없는 것 |
| --- | --- |
| 사이트 접속 → 엑셀 다운로드 | ERPia 쪽 전부 (주문수집·매출처리·물류대기·물류관리) |
| 주문매핑 화면의 자동수집 | 나머지 전부 (메일·사이트, 매출처리, 물류대기, 물류관리) |
| 업체 전용 화면 하나 (예: 외부 시스템 연동 화면의 한 단계) | 나머지 전부 |

- 반복 대상은 코드에 **목록으로** 둔다 (대상 id → 화면 작업). 엔진은 그 하나만 돈다. 여러 개를 고르는 길은 화면에서도, 예약 줄에서도 막는다 (예약 줄 끝 기능이 반복 대상이면 하나만 받는다).
- 반복 대상에 로그인·화면 진입처럼 **앞에 꼭 필요한 단계**는 엔진이 자동으로 앞에 붙인다 (지금 ERPia 기능을 고르면 실행·로그인이 붙는 것과 같다).

### 실행 창 — 사람이 [실행] 을 누르기 전에 고른다

```
[실행할 기능]  ( ) 보통 실행   (•) 반복 실행
                                   반복할 작업  [주문매핑 — 자동수집 ▼]   ← 하나만 (목록 상자)
                                   간격 [5]분 (1~60)   동안 [60]분 (최대 60)
               보통 실행 체크 칸들 → 반복 실행을 고르면 전부 잠긴다
```

- [반복 실행] 을 고르면 기능 체크가 모두 잠기고, 반복할 작업은 **하나만** 고르는 목록이다 (체크 여러 개가 아니다).
- [실행] → 지금부터 '동안' 분까지, 끝 시각 포함 (예: 12:07 에 60분 → 13:07 까지, 12:07·12:12·…·13:07).
- 기능 고정 빌드면 그 빌드에 든 기능 안의 작업만 목록에 나온다.

### 예약 — 문법과 화면

- 지금 `auto_run_times` 한 줄은 **시작 시각**이다. 시간대 줄을 더한다: `평일 12:00~13:00 5분 <반복 대상 하나>` — `~` 와 `N분` 이 있으면 시간대 반복. 시간대는 60분 이하.
- 같은 날 여러 시간대 가능 (`평일 12:00~13:00 5분 …` + `평일 17:00~18:00 10분 …`). 줄 수 상한 12 안에서.
- 실행 창 [예약] 탭: [반복] 에 '시간대' 를 고르면 끝 시각·간격 칸과 반복할 작업 목록(하나)이 나온다.
- 시간대 안에 다른 예약 줄이 걸리면 지금 규칙("앞 회차가 아직 돈다")대로 건너뛰게 된다 → **[추가] 할 때 겹침을 알리고 막는다.**
- 웹 [실행] 은 PC 의 지금 선택(보통/반복)을 따른다.

## 6. 사용량·서버

- 실행 시작(`run_start`) 은 1번 → 서버 하루 50실행 상한에 1만 든다. 조회 횟수와 무관.
- 사용량: 서버 `refresh_usage` 는 단계 id 넷(`mailbox`·`sales`·`logistics_wait`·`logistics`)만 센다 (`server/schema.sql` 9절). 새 기능은 `usage_daily` 컬럼과 `refresh_usage` 를 같이 고친다 (스킬 `server-sql`). **한 번이라도 저장했을 때만 1** (사용자 결정 10-06 — "할 일이 없어 건너뛰면 세지 않는다" 와 같은 원칙). 조회만 하고 저장할 것이 없었으면 0.
- 이벤트: 빈 조회마다 사용자 로그를 보내지 않는다 (상세 표에만). 저장했을 때만 한 줄 → 하루 2만 이벤트 상한과 멀다.
- 심박은 실행 중 30초마다 가므로 끊김 판정(10분)에 걸리지 않는다.
- 웹 실행 상세: "지켜보는 중 — 다음 조회 12:35 · 저장 3번 7건".

## 9. 다른 RPA 를 기반으로 옮길 때

- 엔진·계약은 이 프로젝트의 프레임워크에 묶이지 않는다. 그 RPA 의 대기·중단·로그 방식에 맞춰 **같은 계약**(`prepare`·`count`·`process`)으로 만든다.
- 먼저 볼 것: 그 RPA 에 예약·반복 실행이 있나, 실행 단위 집계를 어떻게 하나, 실행 중 일시정지·중단이 있나.
