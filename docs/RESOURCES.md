# 자원 사용량 / 탐색 계측 (2026-09-08)

RPA 는 오래 켜두고 반복 실행할 프로그램이라 **누수와 CPU 점유**를 재야 한다.
이 문서는 실측값이다. 추정치를 적지 않는다.

측정 도구

| 도구 | 용도 |
| --- | --- |
| `tools/probe_resources.py` | CPU / 워킹셋 / private / 핸들 / 스레드 / GDI / USER 샘플링 (읽기 전용) |
| `tools/probe_search_trace.py` | 컨트롤 탐색 집계. 캐시 후보·위험 자동 판정 (읽기 전용) |
| `tools/test_flow.py --trace --resources` | 1회 실행에 위 둘을 붙인다 |

`psutil==7.2.2` 는 **계측 전용**이다. `build_run.spec` 의 `UNUSED_LIBS` 로 exe 에서 제외한다.

## 1. 결론

| 질문 | 답 |
| --- | --- |
| 메모리 누수가 있는가 | **없다.** 3회 연속 실행에서 회차당 private +1.0MB, 핸들 +7 (2→3회차는 +0) |
| COM/UIA 객체가 쌓이는가 | **안 쌓인다.** COM 래퍼 수 회차당 +0, GDI/USER +0 |

| PC 수명에 영향이 있는가 | 이 수치로는 없다. 실행은 1회 100초, 나머지 시간은 대기다 |
| 오래 켜둬도 되는가 | 프로세스를 계속 띄워 두는 구조라면 문제없다. 다만 아래 5번 참고 |

### ★ 측정에서 두 번 틀렸던 것 — 그룹 분리

`start_new_instance()` 가 **ERPia 를 파이썬의 자식 프로세스로** 띄운다.
그래서 "RPA 프로세스와 그 자식"을 그대로 더하면 ERPia 가 통째로 섞인다.

| 집계 방식 | RPA 로 잡힌 값 |
| --- | --- |
| 자식 전부 포함 (틀림) | 워킹셋 892MB / 스레드 200 / 핸들 4912 |
| 이름만 제외 (여전히 틀림) | 워킹셋 528MB / 스레드 197 |
| **이름 + 하위 트리 제외 (맞음)** | **워킹셋 64MB / 스레드 8 / 핸들 359** |

ERPia 는 이름이 다른 자식 프로세스를 띄운다. **하위 트리째 빼야 한다.**
`probe_resources.py` 가 그룹에 포함된 프로세스 이름을 보고에 찍는 이유다.

2회차 이후 회차당 평균 증가: 워킹셋 +0.9MB / private +1.0MB / **핸들 +7.0** /
스레드 +0.5 / GDI +0 / USER +0 / gc객체 +1.5 / **COM래퍼 +0**

- 핸들은 1→2 회차 +14, 2→3 회차 **+0** 으로 평탄해진다. 누적 누수로 보이지 않는다
- 실행 시간이 회차마다 99 ~ 104.5초로 일정하다. 느려지지 않는다
- **3회 모두 성공.** 중간 실패 없음

> 더 긴 구간(20회 이상)은 아직 안 돌렸다. 지금 수치로는 회차당 +1MB 이므로
> 100회를 돌려도 +100MB 수준이지만, **확인한 것은 3회까지다.**

## 4. 컨트롤 탐색 집계 (1회 실행 102.3초)

| 층 | 호출 | 총 시간 | 구간 대비 |
| --- | --- | --- | --- |
| `search_shallow` | 39회 | 34.5초 | 34% |
| `search` | 23회 | 2.7초 | 3% |
| (`find` 는 위 둘을 감싼다) | 27회 | 34.0초 | - |

**탐색이 전체 시간의 약 37%다.** 상위 항목:

| 조건 | 총초 | 회 | 판정 |
| --- | --- | --- | --- |
| `Frm_Management_Logistics` Pane | 14.4 | 4 | **못찾음** |
| `Frm_Management_HoldLogisticsStandard` Pane | 14.2 | 4 | **못찾음** |
| `imgLbl_Logistics` / `imgLbl_OrderCollect` / `imgLbl_HoldLogistics` | 각 0.9 | 각 1 | 1회 |
| `btn_DeleteSlip` | 0.8 | 2 | 캐시후보 |
| `gridCtrl_Order` | 0.3 | 2 | 캐시후보 |

### ★ 시간을 먹는 것은 중복 탐색이 아니라 "없는 것을 찾는 비용"이다

화면 전환을 기다리는 동안 화면 Pane 이 아직 없으면, **조기 종료가 걸리지 않아
트리를 `MAX_SEARCH_DEPTH`(12층)까지 끝까지 훑는다.** 1회 1.5초, 실패 판정까지
4회 반복해서 화면 하나당 14초다. 두 화면 합쳐 **28.6초**로 탐색 시간의 대부분이다.

| 계측 회차 | 화면 Pane 1회 탐색 |
| --- | --- |
| 1회차 (다른 인스턴스 존재) | 10.9초 |
| 2·3회차 (단독) | 1.5초 |

**같은 코드가 환경에 따라 7배까지 흔들린다.** 절대 시간을 전제로 timeout 을 잡으면 안 된다.

→ 개선 방향: `find()` 에 **깊이 제한**을 준다. 화면 Pane 은 5층에 있는 것이 확정값이라
   6층까지만 보면 "없음" 판정이 즉시 끝난다. 캐시(4종 / 1.2초)보다 효과가 훨씬 크다.

### ★ 환경 변동으로 흔들리는 조건 — 1건 발견

```
위험(일치 [2])   control_type='Button', title_re='열기.*|Open.*|확인.*'
```

파일 선택 창의 [열기] 버튼이 **2개 잡힌다.** 현재 코드는 경고를 남기고 첫 번째를 쓴다.
지금은 맞지만 **순서가 보장된 것이 아니다.** 조사해서 조건을 좁혀야 한다.
캐시 대상에서도 제외해야 한다.

`probe_search_trace.py` 는 이런 조건을 자동으로 표시한다. 판정 기준:

| 판정 | 조건 |
| --- | --- |
| 캐시후보 | 2회 이상 찾았고 **매번 정확히 1개** |
| 위험 | 일치 개수가 2개 이상이거나 호출마다 달랐다 |
| 못찾음 | 0개가 나온 적이 있다 (대기·재시도 경로) |

## 5. 안정화 관점에서 나온 사실

1. **ERPia 는 RPA 파이썬의 자식으로 뜬다.** 부모가 죽어도 같이 죽지 않고 **고아로 남는다.**
   실제로 테스트 뒤 로그인된 인스턴스가 남아 다음 실행이 중복 로그인에 걸렸다
2. **`close_others()` 는 종료 완료를 기다리지 않고 반환한다.** 직후에 세면 아직 살아 있다
   (소크 2·3회차에서 잔여 1개로 잡혔고, 잠시 뒤 확인하니 0개였다)
   → 종료 후 **사라질 때까지 대기**하는 경로가 필요하다
3. 계측 도구 자신도 부하다. `process_iter()` 를 매 샘플마다 돌렸더니 **샘플러가 CPU 13%**
   를 썼다. 대상 목록 갱신 주기를 3초로 분리해 3.3% 로 낮췄다
