# 화면별 컨트롤 식별표 (확정본)

`docs/UI_SURVEY.md`가 조사 원본·이력이라면, 이 문서는 **코드가 참조하는 확정값**이다.
조사로 실제 확인된 것만 적는다. 추측값을 넣지 않는다.

식별 우선순위: `automation_id` > `control_type` + `title` > `class_name`
인덱스(`found_index`)는 최후수단이며 사용 시 사유를 코드 주석에 남긴다.

| 상태 표기 | 뜻 |
|---|---|
| 확정 | 덤프로 확인, 코드에서 사용 중 |
| 관찰 | 스크린샷으로만 확인, 덤프 미확보 |
| 미조사 | 확인 안 됨. 구현 금지 |

### ★ 행 단위 접근 — 가능

```
데이터 패널 (Custom)
  └ ListItem  title="행 2"                    ← 행
      ├ DataItem title="row Check Box 행 2"   ← 체크박스 셀
      ├ DataItem title="사이트코드 행 2"
      ├ DataItem title="마켓명 행 2"
      └ ...
  └ ListItem  title="행 1"
      └ DataItem title="Group Row"            ← 마켓별 그룹 헤더 행
```

- 행: `child_window(title="행 N", control_type="ListItem")`
- 셀: `child_window(title="<컬럼명> 행 N", control_type="DataItem")`
- 그룹 행 판별: 하위에 `Group Row` DataItem이 있음

### ★ 셀 값은 `window_text()` 로 읽으면 안 된다

DataItem의 **Name은 값이 아니라 `<컬럼명> 행 N` 형식의 식별자**다.
`window_text()` 로 읽으면 `<사이트코드>` 가 아니라 `'사이트코드 행 2'` 가 나온다.

2026-09-04에 이것 때문에 사이트코드를 하나도 찾지 못했다.

값은 `utils/ui.py` 의 `cell_value()` 로 읽는다. 순서는 다음과 같다.

1. Value Pattern (`iface_value.CurrentValue`)
2. LegacyIAccessible `Value`
3. 하위 Text control 들의 텍스트
4. `window_text()` — 단 `<컬럼명> 행 N` 형식이면 값이 아니므로 버린다

**주의 — 가상 스크롤**: DevExpress 가상화라 **화면에 보이는 행만 UIA에 노출된다.**
덤프 시점에 주문 그리드는 `행 1~6`, `행 60~74`만 있었다(실제 34건/1,228건).
→ 전체 건수를 ListItem 개수로 세면 안 된다. 전체 순회에는 스크롤이 필요하다.
→ 전체선택은 헤더 체크박스 한 번이면 되므로 영향 없다.

### ★ 컨트롤 탐색 시 주의 — `descendants()` 금지

`wrapper.descendants(**kwargs)` 는 **ElementInfo 인자**(process / class_name /
control_type / title)만 받는다. **`auto_id` 와 `title_re` 는 조용히 무시된다.**
예외도 안 나고 빈 결과가 나온다.

2026-09-03에 이것 때문에 두 번 헤맸다.
- 사이트 그리드(`gridCtrl_SiteList`)를 못 찾음
- 사이드바 `주문수집` 텍스트 검색 실패

**반드시 `utils/ui.py`의 `search()` 를 쓴다.** 내부적으로
`findwindows.find_elements(parent=..., top_level_only=False, **criteria)` 를 호출하며
pywinauto 조건명을 그대로 받는다.

2. **`Select` 가 성공하지만 아이콘은 안 눌린다.** 셀을 '선택'만 한다.

언어·버전·해상도와 무관하게 고정된 값이다.

```
Button(title='열기', auto_id='DropDown')   ← 파일명 입력창 오른쪽 화살표. 2개 있다
SplitButton(title='열기(O)', auto_id='1')  ← 진짜 [열기]
```

`Button` 을 `SplitButton` 보다 먼저 보던 이전 코드는 **화살표를 눌렀다.**
그것이 실패해서 `[입력창 Enter]` 폴백으로 넘어가 **우연히 동작하고 있었다**
(2026-09-08 탐색 계측에서 "일치 2개"로 잡혀 발견).

**금지 — `auto_id` 만으로 찾으면 안 된다.**
파일 목록의 `ListItem` 에도 숫자 auto_id 가 붙어서 `auto_id='1'` 이 파일에 걸린다.
반드시 `control_type` 을 함께 건다.

### ★ 스크롤 없이 그리드 전체를 읽을 수 있나 — **없다** (2026-09-10 조사)

"보이는 행만 노출된다"를 우회할 길이 있는지 전수로 확인했다
(`tools/probe_grid_access.py`, `tools/test_grid_bulk.py`). **전부 막혔다.**

| 경로 | 결과 |
| --- | --- |
| `Grid` 패턴 `GetItem(행, 열)` | **패턴이 없다.** 전체 행 수도 알 수 없다 |
| `Table` 패턴 | **없다** |
| `ItemContainer.FindItemByProperty` | `Is...PatternAvailable` 은 **true 라고 답하는데** `GetCurrentPattern` 은 빈 값을 준다. 즉 **플래그가 거짓말을 한다** |
| `Ctrl+A` → `Ctrl+C` (클립보드 복사) | 클립보드에 **아무것도 들어오지 않는다** (10초 대기, 행 선택 후에도 동일) |
| `Ctrl+F` 찾기 패널 | 새 Edit 이 생기지 않는다. **꺼져 있다** |
| 자동 필터 행 | 그리드 하위에 `Edit` 이 **0개**. 없다 |
| `ScrollItem.ScrollIntoView` | 행에는 **있다.** 다만 **이미 실체화된 행**만 데려올 수 있어 쓸모가 없다 |

★ **`Is<이름>PatternAvailable` 속성을 믿지 말 것.** 이 프로그램은 지원하지 않는
  패턴도 true 로 보고한다. 반드시 `GetCurrentPattern` 으로 실제 획득까지 확인한다.

결론: **목표 행을 찍어서 데려오는 방법이 없다.** 값으로 찾으려면 그 행이 이미
화면에 있어야 하고, 화면에 오게 하려면 스크롤해야 한다. 순환이다.
그래서 지금의 "끝까지 훑는다"가 우회가 아니라 **유일한 경로**다.

읽기 비용을 줄이려면 훑는 방법이 아니라 **훑는 횟수**를 줄여야 한다
(예: 보류 검증을 전수 스캔이 아니라 체크한 행 번호만 대조하도록). 아직 하지 않았다.

### ✗ "같은 인증번호 재발송" — **확인되지 않았다. 판정을 되돌렸다** (2026-09-21)

09:23 실행이 120초 실패한 뒤 대화가 미읽음으로 돌아와 있었고 본문은 직전 번호 그대로였다.
처음엔 "메일 사이트가 같은 번호를 재발송했다" 로 보고 읽음→미읽음 전환을 새 문자로 골랐다.
**틀린 추론이었을 수 있다** — 폰 쪽 미읽음이 동기화로 되살아난 것과 **구별할 수 없었다**
(그때 대화창이 비어 수신 시각을 못 봤다). 그 판정은 **만료된 지난 번호를 넣고**, 반복되면
**계정이 잠긴다.** 그래서 되돌렸다: 본문이 요청 전과 같으면 미읽음이어도 **고르지 않는다.**

- 뒷받침: 같은 날 13:30 실행에서 **목록 미리보기가 대화창보다 늦게** 바뀌었다(대화창 경로로
  먼저 잡혔다). 미읽음과 미리보기가 같은 문자열에서 나와도 **갱신 시점은 어긋날 수 있다.**
- 요청 전 목록을 **못 찍으면**(UIA 순간 오류) 목록 경로를 끈다(`_LIST_BASELINE`). 기준이 비면
  목록에 남은 지난 번호를 새 것으로 고른다.

### ★★ 대화창이 비던 진짜 이유 — **가려진 창을 좌표 클릭했다** (2026-09-21)

`open_conversation()` 이 `item.click_input()` 을 **앞으로 가져오지 않고** 불렀다. 좌표 클릭은
창이 가려져 있으면 **위에 있는 창을 누른다**(`utils/ui.bring_forward` 주석, 09-10 실측).
인증 중에는 브라우저가 앞에 있어 **대화가 열리지 않았고 메일 사이트 화면 어딘가가 눌렸다.**

| 실행 | 모니터 | 요청 전 본문(목록+대화창) |
| --- | --- | --- |
| 09-18, 09-21 오전·13:17·13:18 | 1 / 2 | **1건** (대화창 0건 — "비어 있음") |
| 09-21 13:30 (`bring_forward` 뒤 클릭) | 2 | **34건** (대화창이 채워졌다) |

사용자가 처음 짚은 "모니터가 1개면 인증번호를 못 받는 것 같다" 의 실제 원인 하나가 이것이다
(모니터가 1개면 브라우저가 앱을 덮는다). → 이제 **앞으로 못 가져오면 누르지 않는다.**
`_press()` 의 클릭 폴백도 같다.

### 아직 확정하지 못한 것 — '다시 연결' 버튼

폰이 끊긴 상태에서 화면을 훑었지만 재연결 버튼이 **없었다.** 그때 보인 버튼은
최소화/최대화/닫기, 휴대폰 화면 열기, 연결 카드, 새로 고침, 방해금지·볼륨·오디오·
소리 재생, 알림 지우기, 기타 옵션, 새 메시지, 최근/숨김, 스크롤, 전화 걸기,
이모지/GIF/이미지 첨부/보내기 — 그뿐이다.

그래서 `collect/phonelink.reconnect()` 는 **auto_id 를 추측하지 않는다.**
보이는 이름으로 찾고(`다시 연결|재연결|연결 시도|다시 시도|Reconnect|Try again`),
못 찾으면 **그 순간 화면의 버튼 이름을 전부 로그에 남긴다.**
버튼이 실제로 뜨는 순간 `tools/probe_phone_window.py --dump` 로 이름을 확정할 것.

### ★ 컨텍스트 메뉴는 별도 최상위 창이다 (2026-09-07 확정)

DevExpress 컨텍스트 메뉴는 부모 창의 자식이 아니라 **제목 없는 별도 최상위 창**으로 뜬다.


찾는 범위에 따라 속도가 크게 다르다. 실측값이다.

| 방법 | 시간 |
|---|---|
| 팝업 창 안에서만 검색 | **0.06초** |
| `find_elements(process=pid, control_type, title)` | 6.6초 |
| `find_elements(process=pid, title)` | 10.8초 |
| `process_menu_items()` (타입별 전체 순회) | 41.5초 |

정작 실패 진단 목록에는 그 항목이 찍혀 나왔다.

→ `ui.popup_menu_windows(pid)` 로 팝업 창을 먼저 찾고 그 안만 본다.
   못 찾으면 마지막에 한 번만 프로세스 전체로 넓힌다(`find_menu_item(..., deep=True)`).
   물류대기 / 물류관리 **둘 다 같은 `ui.click_process_menu_item()` 을 쓴다.**

#### ★ 드롭다운도 가상 스크롤이다 — 보이는 것만 보면 "없다" 고 한다 (2026-09-10)

**실행 중에 실제로 겪었다.** 택배사 드롭다운을 열었는데 `찾지 못했다` 로 끝났고,
사람이 같은 목록을 **손으로 스크롤해 내리니 그 택배사가 있었다.**

원인은 그리드와 같다. `List` 는 **지금 그려진 `ListItem` 만** UIA 에 노출한다.
`ui.dropdown_items()` 는 `List.children()` 을 읽으므로 한 화면 분량만 본다.
위 "확인된 항목" 도 **그때 보이던 것까지**였을 수 있다.

고친 방식 (`utils/ui.py`):

| 순서 | 하는 일 |
| --- | --- |
| 1 | 보이는 목록에서 완전 일치를 찾는다 (대부분 여기서 끝난다) |
| 2 | 없으면 **맨 위로 올린 뒤** 한 페이지씩 내려 가며 찾는다 |
| 3 | 끝까지 못 찾으면 **훑으면서 본 이름 전부**를 예외 메시지에 담는다 |

2번에서 맨 위로 먼저 올리는 이유: 콤보는 **지금 선택된 항목 위치에서** 열릴 수
있다. 아래로만 훑으면 위쪽 항목을 통째로 놓친다.

움직이는 수단은 그리드와 같은 순서로 본다. **항목 이름 목록이 실제로 바뀌었는지로
성공을 판정한다** — 예외가 없다고 움직인 것이 아니다.

| 수단 | 내용 |
| --- | --- |
| `ScrollBar` | 목록 안 수직 스크롤바의 `페이지 아래로` Invoke. 부작용이 없다 |
| `ScrollPattern` | 목록이 Scroll 패턴을 지원하면 그것으로 |

어느 수단이 먹었는지는 실행할 때 **한 번 INFO 로 남는다**
(`드롭다운 스크롤에 ScrollBar 가 먹는다`). 환경마다 다를 수 있어서다.

→ **찾기만 하려다 값을 바꾸는 수단은 두지 않는다.** 휠은 코드에서 제거했다.

함께 넣은 안전장치

### ★★★ 계측 코드가 무동작이었다 — `tuple(RECT)` 를 쓰면 안 된다

원인을 세 실행이나 못 찾은 진짜 이유가 이것이다.

    tuple(ctrl.rectangle())   # TypeError: 'RECT' object is not iterable

pywinauto 의 `RECT` 는 ctypes 구조체라 **iterable 이 아니다.** 이렇게 쓴
비교 코드가 매번 예외로 빠져 **위치 진단이 통째로 동작하지 않았고**,
그 상태에서 나온 "위치가 안 변했다" 를 근거로 **엉뚱한 결론까지 냈다.**

- 반드시 `ui.rect_of(ctrl)` 를 쓴다 — `(left, top, right, bottom)` 을 돌려준다
- **단위 테스트의 가짜 컨트롤도 실제 `RECT` 를 돌려주게 만든다.** 평범한 튜플로
  만들면 이 버그를 못 잡는다 (실제로 못 잡았다)

같은 버그로 `ui.wait_rect_settled()` 도 **첫 읽기가 None 이라 항상 즉시 True**
였다. 즉 "멎을 때까지 기다린다" 가 한 번도 실행된 적이 없었다.

### 고친 방식

`ui.recheck_cell()` 이 누르기 직전에 **행 번호로 셀을 다시 잡고**
(`'엑셀업로드 행 16'` — 행 번호가 곧 신원이다), `ui.wait_rect_settled()` 로
**위치가 멎을 때까지 기다린 뒤** 넘긴다.

> ★ 일반 규칙: **좌표를 저장하지 않는 것만으로는 부족하다.**
> 움직였을 수 있으면 누르기 직전에 **신원으로 다시 잡고 멎기를 기다린다.**

| `실패` | **주문이 없었거나**, **로그인에 실패했거나** — 두 가지가 섞여 있다 |

그래서 셋 다 다음 두 가지에 쓰면 안 된다.

1. **완료 판정** — `수집중` 이 남았다고 더 기다리면 끝나지 않을 것을 기다린다
2. **결함 보고** — `실패` 는 주문이 없을 때도 뜬다. 결함이라고 단정하면 오보다

### 실제로 잘못 읽은 적이 있다

2026-09-15 전체 실행에서 `성공 1, 수집중 4, 실패 1` 이 나왔고, 이것을
**"수집중 4건이 남았는데 넘어갔다 = 매출처리가 일부를 놓쳤다"** 로 보고했다.
**틀린 해석이다.** 그 4건은 로그인에서 막힌 것일 수 있어 기다려도 끝나지 않는다.

### 코드는 어떻게 하고 있나

| 위치 | 상태표를 쓰나 |
| --- | --- |
| `wait_collect_started` / `wait_collect_done` (완료 판정) | **쓰지 않는다.** 매출처리 버튼의 활성 여부로만 본다 |
| `_collect_progress()` | 로그 한 줄. 판정에 쓰지 않는다 |
| `collect_failures()` | `실패` 를 눈에 띄게 남기되 **원인을 단정하지 않는다** |

완료 판정에 다른 신호를 쓰려면 **무엇을 쓸지 먼저 확정해야 한다.** 아직 없다.

## ★ "조회가 끝났다" 신호는 없다 — 그래서 0행이 130초였다 (2026-09-15 실측)

물류관리 `prepare()` 가 **하단 0행일 때 130초**를 썼다. 상한이 그대로 소요시간이 됐다.

    17:40:44  이미 등록모드다
    17:40:54  행이 나타나지 않았다      ← control 10초를 통째로
    17:40:55  주문조회(J)
    17:42:55  행이 나타나지 않았다      ← long_task 120초를 통째로

`_wait_rows` 가 **"행이 나타나면 반환"** 이라, 진짜 0행이면 빠져나올 길이 없었다.
배터리 133초 / 충전기 131초로 **환경과 무관**했다. 구조 문제다.

### 조사: 조회 중에 바뀌는 UIA 값을 전부 찾아봤다 — 없다

`tools/test_query_signal.py` 로 `주문조회(J)` 를 누르기 전과 누른 뒤 15초를 견줬다.

| 신호 | 누르기 전 | 누른 뒤 15초 |
| --- | --- | --- |
| 하단 행 수 | 0 | 0 (12표본 전부) |
| `btnSearch` / `btnInsert` / `btnSave` / `Btn_Search_JuMun` 활성 | `O . O O` | `O . O O` (전부 동일) |
| `IsHungAppWindow` | 아니오 | 아니오 |
| 최상위 창 개수 | 1 | 1 (진행 창이 뜨지 않는다) |

**조회 중에 회색이 되는 버튼도, 뜨는 진행 창도 없다.** `IsHungAppWindow` 는
5초 넘게 먹통이어야 참이 돼서 짧은 조회를 아예 못 잡는다.

### 쓸 수 있는 신호: Win32 UI 스레드 왕복

`SendMessageTimeout(hwnd, WM_NULL)` 은 대상 창의 **메시지 펌프가 차례가 와야**
답한다. 곧 "저 프로그램이 지금 얼마나 밀려 있나" 다.

| 상태 | 왕복 |
| --- | --- |
| 유휴 | **0.1ms** |
| `주문조회(J)` 직후 | **6.3ms** (60배) |

비용이 0.1ms 라 폴링에 넣어도 부담이 없다. 같은 판정을 UIA 로 하면
**버튼 4개에 1.8초**(개당 0.44초)다. 행 수 읽기는 0.045초.

→ `utils/winprobe.ui_roundtrip()`.

### 고친 방식 — `logistics._wait_rows_settled()`

| 상태 | 판정 |
| --- | --- |
| 행이 나왔다 | 즉시 반환 (예전과 같다) |
| 행이 없고 ERPia 가 **한가**하다 | 유예 뒤 0행으로 확정 |
| 행이 없는데 ERPia 가 **바쁘다** | 계속 기다린다 (상한까지) |

마지막 줄이 안전장치다. **조회가 정말 오래 걸리면 예전처럼 끝까지 기다린다.**
빨라지는 것은 "할 일이 없어서 0행" 인 경우뿐이다.

> ★ 왕복은 조회가 **UI 스레드에서 돌 때만** 잡힌다. 백그라운드 스레드로 돌면
> 한가해 보인다. 그래서 이것만으로 판정하지 않고 **유예(`settle`)를 함께** 둔다.

**실측: 130.0초 → 12.8초** (2026-09-15, 같은 0행 조건). 안전장치는 네 경우로
따로 확인했다 — 행 즉시 등장 / 0행+한가 / 0행+계속 바쁨(상한까지 감) /
바쁜 동안 기다리다 행 등장(놓치지 않음).

전체 실행에서도 확인했다 (2026-09-15). **하단에 행이 있으면 1초 만에 끝난다** —
기다릴 이유가 없으므로 즉시 반환한다. 12.8초를 쓰는 것은 0행일 때뿐이다.
탐색 집계가 그대로 보여준다.

| 조건 | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| `ListItem '^행 N$'` 못찾음 | 416회 25.15초 | **55회 5.48초** |
| 물류관리 구간 전체 | 140.4초 | **32.7초** |

## ★ 컨트롤 탐색이 느린 이유와 해결 (2026-09-07 계측)

이 프로그램은 UIA 트리가 크다. **메인 창 하위 2,971개, 물류관리 화면 하나만도 1,133개.**

`findwindows.find_elements` 는 조건과 무관하게 하위 트리를 **끝까지** 훑는다.
그래서 버튼 하나를 찾는 데도 다음이 걸린다.

| 탐색 | find_elements | 층별 조기종료 |
| --- | --- | --- |
| 메인 창에서 화면 Pane (`Frm_Management_Logistics`, 5층) | 4.28초 | **1.07초** |
| 화면에서 하단 그리드 (`gridCtrl_BS_Bottom`, 4층) | 2.36초 | **0.55초** |
| 화면에서 저장 버튼 (`btnSave`, 3층) | 2.39초 | **0.33초** |

물류관리는 진입~전체선택까지 이 탐색을 예닐곱 번 반복한다.
그래서 **클릭 자체는 0.3초인데 전체선택까지 19초**가 걸렸다.

→ `utils/ui.py` 의 `search_shallow()` 가 `children()` 으로 층을 내려가며
**맞는 것이 나온 층에서 멈춘다.** `find()` / `exists()` 가 이것을 쓴다.
결과는 `search()` 와 동일함을 확인했다(2026-09-07).

> **전체 순회를 `children()` 으로 바꾸는 것은 오히려 느리다** (헤더 46개 탐색:
> find_elements 0.20초 vs 층별 전체순회 1.61초). 빨라지는 이유는 조기 종료다.
> 그래서 `search()`(전부 찾기)는 그대로 두고 `find()`(하나 찾기)만 바꿨다.

`title_re` 같은 정규식 조건은 `search_shallow` 가 지원하지 않고 `search` 로 넘긴다.

로그인 창과 같은 구조다(중첩 Edit + 숫자 auto_id). 로그인 때 겪은 함정이 여기서도 그대로다.

비밀번호는 `config/settings.local.json` 의 `excel_passwords`(사이트명별) 또는
`excel_password`(기본값)에서만 읽는다. **창이 떴는데 설정에 값이 없으면 아무 값도
넣지 않고 중단한다.** 틀린 값을 반복해서 넣지 않기 위해서다.

### 업로드 결과 판정

- 실패: 제목 `ERPia` 팝업이 뜬다. 본문에 사유가 그대로 나온다
  (실측: `헤더 개수가 일치하지 않습니다. (현재 세팅 헤더 개수: 8, 업로드 엑셀 헤더 개수: 5)`)
- 성공: 팝업이 뜨지 않는다. `업로드 오류 팝업 없음. 정상으로 본다.`

★ **비밀번호가 맞았는지는 이 팝업으로 알 수 있다.** 헤더 개수를 읽었다는 것은
파일이 열렸다는 뜻이다.


## 메시지 팝업 (ERPia 공통) — 확정 (2026-09-10 실측)

| 요소 | 값 |
| --- | --- |
| 창 | `Window auto_id="Popup_ERPiaMessageBox"` (제목은 내용에 따라 다르다. 실측 예: `입력누락`) |
| 본문 | 하위 `Text` 들의 이름. 실측 예: `연락처를 입력하세요` |
| 버튼 | `확인(O)` = `Button auto_id="btn_확인(&O)"`, `닫기` |

★ **탐색이 막히지 않는다.** 실측 **0.03초**에 찾아 제목·본문·버튼을 모두 읽었다.
  "모달이 떠 있으면 UIA 호출이 63초씩 막힌다"(2026-09-04 기록)는 이 팝업에는
  해당하지 않는다.

★ **[확인] 하나뿐이면 누르고 다음 단계로 넘어간다** (사용자 확정 2026-09-22, 09-10 "누르지 않는다" 를 대체).
  글은 리포트 '확인할 것' 에 남는다. [예]/[아니오] 처럼 고르는 팝업은 누르지 않는다.
  코드: `utils/dialogs.dismiss_message_box()` — 물류관리 저장 실패(`logistics.close_save_failure`),
  물류대기 저장 뒤, 그리고 ERPia 단계가 실패했을 때 (`Hooks.recover`).

## 물류관리 하단 그리드 — 전체선택과 체크박스는 다른 것이다 (2026-09-10)

| | 무엇 | 어떻게 |
| --- | --- | --- |
| 전체선택 | 행 **선택** | `매출구분` 헤더 왼쪽 인디케이터 셀 클릭 (`ui.click_row_indicator`) |
| `배송등록` | 행별 **체크박스** 컬럼 | 전체선택 수단이 **아니다.** 값은 `선택` / `선택안됨` |

`row Check Box` 헤더는 이 그리드에 **없다** (`ui.header_select_all` 을 쓸 수 없다).
전체선택 성공은 **선택된 행 수로 확인한다** (`logistics.selected_row_count`).
