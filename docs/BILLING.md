## 2. 모듈 = 사람이 고르는 기능 = 행위 단위

사람은 모듈을 고르고, 고른 것만 **고정된 순서로** 돈다. 예: 주문수집·매출처리 +
물류관리 → 주문수집·매출처리 → 물류관리 (물류대기는 건너뛴다).

| 모듈 | 들어가는 단계 | 행위 수 |
| --- | --- | --- |
| 메일 엑셀 받기 | 인증 경로 점검 · 웹메일 로그인 · 받은메일함 | **1** (메일 사이트 한 곳. 처리한 메일이 없으면 0, 09-30) |
| 주문수집·매출처리 | 화면 진입 · 엑셀수집/자동수집 · 매출처리 | **1** (엑셀 10개를 올려도 1) |
| 물류대기 | 물류대기 | 1 |
| 물류관리 | 물류관리 | 1 |
| (자동 포함) | 프로그램 실행 · 로그인 | **세지 않는다** |

- 프로그램 실행·로그인은 ERPia 모듈을 하나라도 고르면 **자동으로** 들어간다.
- 메일 엑셀 받기를 고르지 않으면, 주문수집은 **오늘 매니페스트에 남은 엑셀**을 올린다
  (`consumed_at` 으로 두 번 올리지 않는 보호는 그대로).
- 수집방식(엑셀/자동)은 주문수집·매출처리를 고를 때만 본다.

## 4. 잔액 규칙 (C·D)

```
[실행] → 인터넷/서버 확인 (안 되면 막는다)
       → 계정 잔액 > 0 인가 (0 이하면 막는다 — "충전 뒤 실행")
       → 고른 모듈을 **끝까지** 돈다 (도중에 잔액이 떨어져도 멈추지 않는다)
       → 끝나면 행위를 보고 → **서버가** 잔액을 깎는다 (음수가 될 수 있다)
```

도중에 멈추지 않는 이유: 물류관리 저장 직전에 끊기면 ERPia 에 반쯤 처리된 데이터가 남는다.

## 5. 위변조 방지 — 제안 (E, 미확정)

클라이언트가 행위를 올려 보내는 구조라 고객 PC 에서 조작할 수 있다. exe 에 키를 구워도
뜯긴다(`baked:` 와 같은 한계). 1차 방어로 제안하는 것:

1. **잔액의 주인은 서버다.** 클라이언트는 잔액을 쓰지 못하고, 행위만 보고한다.
   차감은 서버 함수가 한다(Supabase `security definer` 함수 + RLS).
2. **실행 시작을 서버에 먼저 기록한다.** 시작만 있고 종료 보고가 없는 실행은
   대시보드에 드러낸다(강제 종료·조작 신호).
3. 남는 구멍: 개조한 클라이언트가 행위를 **적게** 보고하는 것. ERPia 쪽 주문·출고
   데이터와 대조해야 막히는데, 지금은 그 경로가 없다.
