# 오류 처리 / 재시도 / 재개 (Phase 10 정리)

2026-09-22 기준 (**4-1 / 4-2 는 2026-09-15 추가** — [중단]과 구간 실행. 알림 닫고 다음 단계는 09-22).
**코드를 읽어 정리한 실제 동작이다.** 계획이 아니다.

원칙 세 가지.

1. **실패를 성공으로 넘기지 않는다.** 예외를 삼키는 코드를 두지 않는다
   (`.claude/hooks/check_rpa_rules.py` 가 `except: pass` 를 잡는다)
2. **어디서 실패했는지 로그만 보고 알 수 있어야 한다.** 모든 업무 단계는
   `utils/logger.step()` 으로 감싼다 — 진입 `▶`, 성공 `✔`, 실패 `✕` + 스크린샷
3. **재시도에는 반드시 상한이 있다.** 무제한 재시도와 고정 대기는 금지

## 2. 단계별 실패 시 동작

### 수집 RPA

| 단계 | 실패하면 | 재개 |
| --- | --- | --- |
| 인증 경로 점검 (`auth_code.preflight`) | **시작 전에 중단.** 설정 조합이 틀렸다고 알린다 | 설정을 고치고 다시 실행 |
| 웹메일 로그인 | 중단 + 스크린샷 | 다시 실행 |
| 인증문자 대기 | `sms_code`(120초) 초과 시 중단. **추측한 번호를 넣지 않는다** | 다시 실행 |
| 2차 인증 실패 (받은 번호가 거부됨) | **60초 뒤 한 번 더** 로그인부터 다시 한다 (`webmail.AUTH_ATTEMPTS=2`, 사이 `AUTH_RETRY_DELAY`=60초) | 아래 ★★ |
| 인증번호가 **안 옴** (120초 초과) | **60초 뒤 새로 요청, 최대 2번 더** 그 뒤 중단 (`webmail.CODE_RETRIES=2`, 사용자 확정 09-28). 화면에 한 줄 알린다 | 위와 따로 센다 |
| 메일 열기 | **2회까지** 재시도(`OPEN_ATTEMPTS`). 실패 화면을 남기고 목록으로 복귀 | 그 메일은 실패로 기록 |
| 첨부 다운로드 / 파일 검증 | 그 메일만 실패 처리. **다음 메일은 계속한다** | 아래 ★ |

★ 위 "중단" 은 **메일만 돌 때**다. 통합·실행용에서 뒤에 고른 기능이 있으면 메일 단계가 멈춰도 **뒤 기능으로 넘어간다** —
그 단계는 실패, 남은 메일 단계는 건너뜀, 사유는 '확인할 것', 요약 맨 앞 `끝나지 않은 단계:`, 이력은 `unfinished`
(`full_flow._full`, 사용자 확정 2026-09-30 — 엑셀을 여러 곳에서 받을 때 한 곳 때문에 전부 멈추지 않게). [중단] 과 단계 밖 실패는 그대로 멈춘다.

★ **메일을 읽지 않음으로 되돌리지 않는다** (사용자 확정 2026-09-30 — 09-08 "실패한 메일은 되돌린다" 를 대체).
메일은 열어야 첨부를 받을 수 있고, 여는 순간 읽음이 된다. 받기 실패한 메일은 매니페스트에 `failed` 로 남고,
다음 실행이 그 기록으로 **읽음이어도 다시 연다** (`webmail.retry_keys` — `mail_days_back` 기간 안의 날짜 기록.
한 번이라도 받았거나 엑셀이 아니었던 메일은 빼서 두 번 받지 않는다).

★★ **왜 60초인가.** [휴대폰 연결] 앱은 문자 도착 시각을 **분 단위**로만 준다.
같은 분 안에 인증번호를 다시 요청하면 **직전 번호를 새 것으로 착각**해 또 실패한다
(2026-09-09 2회 재현). 문자마다 어느 사이트 것인지 가리는 로직을 만드는 것보다,
분이 바뀌기를 기다리는 편이 단순하고 확실하다 (사용자 확정 2026-09-09).

**2026-09-10 보강 — 60초 대기에만 기대지 않는다.** 그 대기는 경로를 늦출 뿐
막지는 못했고, 실제로 `_find_code()` 는 같은 분의 직전 번호를 **먼저** 골랐다
(오름차순 정렬 + 첫 건). 지금은 두 가지로 막는다.

| 방어 | 내용 |
| --- | --- |
| 요청 전 스냅샷 | `phonelink.prepare()` 가 대화의 본문 목록을 찍어 둔다. 그때 이미 있던 문자는 인증번호로 쓰지 않는다 |
| 최신 우선 | 남은 후보 중 **가장 나중 것**. 시각이 같으면 대화창에 **나중에 놓인 것** |

adb 경로는 초 단위 시각을 주므로 해당되지 않는다.

**파일 검증** (`webmail.verify_excel`) — "버튼을 눌렀다"와 "쓸 수 있는 파일이 생겼다"는 다르다.

| 확인 | 걸러내는 상황 |
| --- | --- |
| 파일이 생겼는가 | 다운로드가 끝나지 않음 (`download.failure()` 도 함께 본다) |
| 크기가 0이 아닌가 | 세션이 끊겨 빈 파일이 생김 |
| 첫 바이트가 엑셀인가 (`PK` / OLE) | 로그인 페이지 HTML 이 `.xlsx` 이름으로 저장됨 |

내용까지 열어 보지는 않는다. 암호가 걸린 파일이 있어 여기서 판정할 수 없다.
그건 업로드할 때 대상 프로그램이 판정한다.

### ERPia RPA

| 단계 | 실패하면 |
| --- | --- |
| 실행/연결 | 권한(관리자) 불일치면 창이 안 보인다 → `utils/elevation.py` 가 먼저 진단 |
| 로그인 | 팝업 본문을 **읽어서 분기.** 중복 로그인이면 기존 인스턴스를 닫고 재시도, 계정 오류면 즉시 중단. 팝업 처리 **5회 상한** |
| 화면 진입 | `timeouts.window` 초과 시 중단. 어떤 화면이 열렸는지 로그에 남긴다 |
| 사이트 행 찾기 | **완전일치만.** 못 찾으면 중단한다. 비슷한 이름에 올리지 않는다 (되돌릴 수 없다) |
| 엑셀업로드 클릭 | 첫 방법에 넉넉한 시간, 폴백은 짧게. **이미 눌린 것을 또 누르지 않기 위해서다** |
| 파일 경로 입력 | 파일명 칸을 **먼저 비우고** 넣고 **되읽어 확인한다**. 다르면 [열기] 를 **누르지 않고** 실패로 처리한다 — 엉뚱한 파일을 열지 않기 위해서다. 2026-09-10 에 남은 글자가 앞에 붙어(`ns` + 경로) Windows 가 `파일 이름이 올바르지 않습니다` 로 거부한 일이 있었다 |
| 엑셀 비밀번호 창 | 설정에 값이 없으면 **아무것도 넣지 않고 중단.** 틀린 값을 반복 입력하면 잠긴다 |
| 업로드 오류 팝업 | 팝업을 닫고 제목·본문을 그 파일의 실패 사유로 남긴다. 흐름은 멈추지 않는다 — 아래 줄대로 한 번 더 올려 보고, 안 되면 그 파일만 실패 |
| 엑셀업로드 1건 실패 | **한 번 더 올려 본다** (`UPLOAD_ATTEMPTS=2` = 1회 재시도). 두 번 다 실패하면 그 파일만 실패로 남기고 **다음 단계로 넘어간다** — 준비된 엑셀 자체에 문제가 있는 경우이므로 더 시도하지 않는다 (사용자 확정 2026-09-10). 실패 뒤 남은 파일 선택 창은 닫는다 |
| 업로드 N건 중 1건 실패 | **나머지를 계속한다.** 성공/실패를 목록으로 돌려주고 매니페스트에 반영 |
| 업로드 실패의 종류 | `업로드 실패`(파일 창이 안 떠 올리지도 못함) / `등록 실패`(올렸는데 거부됨). 확인할 것이 다르므로 구분해 기록한다 |
| 매출처리 | 수집 0건이면 건너뛰고 다음 단계로 |
| 물류대기 배송보류 | 보류를 다 건 뒤 **하단을 한 번 훑어 실제 보류 수를 대조**한다. 체크한 수보다 적으면 경고를 남긴다 (`verify_holds`) |
| 물류대기 재조회 | 상단 선택을 바꾸면 하단이 다시 조회된다. **맨 위 행의 상품코드가 바뀌고 ERPia 가 한가해지는 것**으로 완료를 판정한다 (`wait_bottom_ready`, 09-15 — 표식 체크 방식은 폐기, `docs/CONTROLS.md` "하단 재조회"). 기다리지 않고 체크하면 그 체크가 날아간다 |
| 물류관리 저장 | 정상이면 팝업 없이 **[등록] 이 활성화**된다. 그것으로 저장 완료를 판정하고 **[운송장출력]** 을 누른다 |
| 물류관리 저장 실패 | [등록] 이 활성화되지 않으면 **운송장출력을 누르지 않는다.** 화면 팝업(`Popup_ERPiaMessageBox`, 예: `입력누락 / 연락처를 입력하세요`)이 **[확인] 하나면 눌러 닫고** 글을 '확인할 것' 에 남긴다 (사용자 확정 2026-09-22 — 09-10 "누르지 않는다" 를 대체). "모달이 뜨면 UIA 가 63초 막힌다" 는 이 팝업에는 맞지 않는다 (실측 0.03초) |
| 물류대기 저장 뒤 알림 | 저장해도 줄지 않았으면 알림을 확인해 [확인] 하나면 닫고 물류관리로 간다 (09-22) |
| **ERPia 단계가 알림에 막혀 실패** | 로그인 뒤 단계(주문매핑 화면·엑셀·자동수집·매출처리·물류대기·물류관리)가 실패했을 때 ERPia 메시지 팝업이 **[확인] 하나로** 떠 있으면 눌러 닫고, 그 단계만 실패로 적고 **다음 단계로 넘어간다** (`Hooks.recover`, 사용자 확정 2026-09-22). 팝업이 없거나 고르는 팝업이면 원래대로 멈춘다 (메일 단계는 2절 수집 RPA 의 ★ — 따로 넘어간다). 주문매핑 화면을 못 열었으면 엑셀·자동수집·매출처리는 건너뛴다 |
| 물류관리 등록 대상 0행 | **오류가 아니다.** 그 전표에 배송보류가 걸려 있으면 배송할 수 없어 개별배송으로 올라오지 않는다. 20초(`REGISTER_TIMEOUT`) 보고 `등록 대상 없음(배송보류 등)` 으로 **정상 종료**한다 (사용자 확정 2026-09-10) |
| 물류관리 출력 창 | `배송요금을 입력하세요` 같은 모달과 출력 창은 **사람이 처리한다** (사용자 확정 2026-09-04) |

### dry-run 은 무엇을 하지 않는가 (2026-09-10 정리)

**상태를 바꾸는 것만** 건너뛴다. 화면 이동·탭 전환·조회는 데이터를 바꾸지 않으므로
dry-run 에서도 실제로 누른다. 예전에는 이동까지 건너뛰어 **로그인 이후를 아무것도
확인할 수 없었다.**

| 한다 | 하지 않는다 |
| --- | --- |
| 화면 진입 / 탭 전환 / 조회(F) / 물류처리 이동 | 행 체크, 배송보류, 물류대기 저장 |
| 부족 상품 판정, `hold_exclude_codes` 적용 | 하단 전체선택, 개별배송 등록 |
| 물류관리 등록모드 준비(모드 전환은 저장이 아니다) | 택배사·박스 적용, 저장, 운송장출력 |
| 엑셀업로드 대상 판정(사이트 행 찾기까지) | 업로드 클릭, 파일 지정 |

모든 대기는 `utils/wait.wait_for` 를 쓰고 **timeout 이 필수**다. 상한 값은
`config/settings.Timeouts` 한 곳에 모아 둔다.

## 4. 중간에 멈췄을 때 어떻게 이어서 도는가

연결은 **`manifest.json` 파일 하나**다. 코드가 서로를 직접 부르지 않는다.

| 상태 | 다음 실행에서 |
| --- | --- |
| `status="downloaded"`, `consumed_at=null` | **올린다** (아직 소비되지 않음) |
| `status="downloaded"`, `consumed_at` 있음 | 건너뛴다 (두 번 올리지 않는다) |
| `status="failed"` | 올리지 않는다. 다음 수집이 이 기록으로 그 메일을 **다시 연다** (읽음 그대로, 09-30) |
| `status="skipped"` | 열어 보니 엑셀 첨부가 아니었다. **읽음으로 두고 다시 열지 않는다** |
| 매니페스트에 이미 있는 메일 키 | 다시 받지 않는다 |

소비 표시는 **사이트명 + 파일 경로로 대조**해서 찍는다. 순서로 맞추지 않는다
(순서로 맞추면 결과가 한 건이라도 어긋날 때 엉뚱한 항목이 소비 처리된다).

| | 동작 |
| --- | --- |
| 어디서 듣나 | `utils/wait.py` 의 조건 대기 안. 조건 확인 전마다 + 폴링 간격에서 |
| 반응 시간 | 상한을 다 쓰지 않는다. **실측: 상한 120초 대기를 0.31초에 빠져나왔다** |
| 예외 | `utils.cancel.Cancelled` — **`BaseException`** 이다 |
| 다음 단계 | 시작하지 않는다. `Hooks.stage()` 가 진입 전에 확인한다 |
| ERPia 창 | **닫지 않는다.** 어디까지 됐는지 봐야 하고, 이어서 붙을 대상이다 |
| 화면 | 오류 창을 띄우지 않는다. 단계 표에 `■ 중단` 으로 남는다 |

★ `Cancelled` 가 `BaseException` 인 이유: `Exception` 으로 두면 경로 곳곳의
`except Exception` 이 취소를 삼켜서 **중단을 눌러도 루프가 계속 돈다.**
그래서 받는 쪽은 반드시 `except cancel.Cancelled` 로 **명시해서** 잡아야 한다.
지금 잡는 곳은 실행 창(`gui/run_app.py` — 잡는 코드는 부모 `erpia_app` 에 있다)과
`tools/test_flow.py` 다 (`tools/test_full.py` 는 중단 토큰 없이 돈다 — 잡을 것이 없다).
새 진입점을 만들면 여기도 넣는다.

## 4-2. 구간 실행 — 어느 단계부터 다시 해도 되는가

**개발 도구 기능이다** (`tools/test_flow --from <단계>`). 실행 창은 구간 실행을 끈다(`run_app.SUPPORTS_SEGMENT = False`) —
사용자에게는 멈춘 기능부터 끝까지 다시 도는 [멈춘 곳부터 다시] 만 있다 (10-02, `orchestrator/modules.resume_from`).
정책이 `orchestrator/steps_erpia.py` 에 **값으로** 박혀 있다. `test_flow` 는 그 값을 보고
확인을 받을지 정한다. 정책을 바꿀 때는 이 문서와 코드를 같이 고친다.

| 단계 | 정책 | 확인 | 확인창에 함께 보여 주는 화면 상태 |
| --- | --- | :---: | --- |
| 프로그램 실행 / 로그인 / 화면 진입 | 안전 | 없음 | — |
| 엑셀수집 | 조건부 | 받는다 | 올릴 파일 목록 |
| 자동수집 | 조건부 | 받는다 | 없음 |
| **매출처리** | **되돌릴 수 없다** | 받는다 | **미매출 주문수** |
| 물류대기 / 물류관리 | 쓰기 | 받는다 | 없음 |

"없음" 은 게을러서가 아니다. 물류 화면의 행 수는 **그 화면을 열어야** 알 수 있고,
여는 것 자체가 그 단계의 일이다. 확인 전에 조작하게 되므로 읽지 않는다.

- 앞 단계를 하지 않으므로 **이미 로그인된 인스턴스에 붙는다**(`erpia_flow.attach`).
  붙을 것이 없으면 **막는다** — 새로 띄우면 "구간 실행" 이 아니라 전체 실행이 된다
- 물류 단계만 할 때는 주문매핑 화면을 **열지 않는다**. 열면 물류 화면에서 되돌아온다
- **물어볼 상대가 없으면 시작하지 않는다.** 콘솔에서 `--yes` 를 주지 않으면 멈춘다
- **통합 흐름(= 실행 창)은 지원하지 않는다.** 실행 창이 단추를 만들지 않고(`SUPPORTS_SEGMENT`),
  `full_flow.run()` 도 막는다. 한쪽만 막으면 표와 실제가 조용히 어긋난다
