# 업무 프로세스 상세

`docs/PROGRESS.md`의 전체 흐름을 화면 단위로 풀어 쓴 문서.
확정된 컨트롤 식별자는 `docs/CONTROLS.md` 에 있다.

자동화 범위: **로그인 → 주문매핑 화면 진입 → 주문수집 → 매출처리 → 물류대기 → 물류관리**
(전부 구현·검증 끝, 2026-09-17 통합 완주). 확정 규칙은 각 Phase 절에 있고 코드는
`automation/` 의 같은 이름 모듈이다.

## 0. 전제 — 실행 권한

ERPia를 관리자 권한으로 띄우는 환경에서는 **RPA도 관리자 권한이어야 한다.**
Windows UIPI 때문에 낮은 권한 프로세스는 높은 권한 프로세스의 창을 볼 수 없다.

`run_admin.bat` 을 쓴다 (`dump_admin.bat` 은 09-18 에 지웠다). 자세한 내용은 `docs/UI_SURVEY.md`.

## 1. 로그인 (Phase 4, 완료)

`automation/login.py`

1. 로그인 창(`auto_id="LoginForm"`) 대기
2. 업체코드 / 아이디 / 비밀번호 입력 (Value Pattern)
3. 로그인 버튼(`lbl_LoginBtn`, Text control) 클릭 — Invoke 불가, `click_input()`
4. 팝업 분기
   - `경고` / "입력된 전화번호가 없어 2차 인증을 할 수 없습니다." → **확인 후 계속**
   - `로그인 실패` / "동시에 같은 아이디로 로그인할 수 없습니다." → **이 PC 의 앞 인스턴스를 닫고 한 번 더 로그인** (`login.close_others`, 09-22 흐름 안에서 확인)
   - `로그인 실패` / "잘못된 아이디 혹은 비밀번호입니다." → **중단**
5. 메인 창(`<업체코드> - <아이디>`) 등장으로 완료 판정

## 3. 주문수집 (Phase 6)

화면 좌상단 버튼: `주문수집` | `상품매핑` (탭)
그 아래: `가져오기` · `사이트 환경설정` · `사이트수집 엑셀세팅`

수집 방식은 설정 `collect_sources` (최소 1, 최대 2 — 둘 다면 엑셀 → 자동 순서) 로 정한다
(`docs/SETTINGS.md` 2절).

### 3-1. 자동수집

1. 사이트 그리드의 **헤더 체크박스**를 클릭해 전체 사이트 선택
   - 그리드는 마켓별 그룹 행(엑셀수집 / 몰A / 몰B / 몰C …)과
     그 하위 사이트 행으로 구성된다
   - 컬럼: 체크 / 사이트코드 / 마켓명 / 사이트명 / 아이디 / 엑셀업로드
2. `가져오기` 클릭
3. 우측 진행 패널(`수집시작`)의 카운터로 진행 관찰
   - `전체` / `수집 중` / `수집완료` / `성공` / `실패`
4. 완료 판정: **하단 주문 그리드 행 수가 0 → n 으로 변함**
   보조 지표로 `조회된 주문수: n건` 텍스트를 함께 확인한다


### 3-2. 엑셀수집

구현 완료 (`order_mapping.upload_excels`, 09-04 확정). 사이트 그리드에서 **사이트명 완전일치**
행의 `엑셀업로드` 셀을 눌러 파일 선택 창에 경로를 넣는다. 컨트롤은 `docs/CONTROLS.md` "엑셀수집".

## 4. 매출처리 (Phase 7)

### 4-1. 하단 주문 그리드

컬럼 (좌→우):
체크 / 사이트 / 마켓명 / 상태 / 주문번호 / 주문시간 / 판매자 코드 / 마켓코드 /
마켓 상품명 / 마켓 규격 / 자체코드 / ERPia 상품코드 / 내품상세 / ERPia 상품명 / ERPia 규격

마켓별 그룹 행 아래에 주문 행이 붙는다.

### 4-2. 매출처리 방법 — 설정 `sales_mode` 로 고른다 (사용자 확정 10-01)

| 방식 | 순서 | 처리 범위 |
| --- | --- | --- |
| `전체` | [매출처리] 단추 → '일괄' 확인 [예] → 결과 "정상매출처리 성공" [확인]. 행은 선택하지 않는다 | **조회되지 않은 미매출 건까지** (매핑되어 있고 정상인 것 — ERPia 가 가른다) |
| `선택주문` | 헤더 전체 체크 → 주문 행 우클릭 → [선택주문 매출처리] → 확인 [예] → 결과 [확인] | 조회된 주문만 |

`order_mapping.process_sales`. 식별값은 `docs/CONTROLS.md` "매출처리 팝업은 2단이다" / "선택주문 매출처리".
09-30 선택주문으로 처리한 주문 1건이 물류대기 [일반]·물류관리에 안 보였다 — ERPia 쪽 문제일 수 있어 **더 보지 않는다** (사용자 결정 10-01).

### 4-3. 팝업 주의

이 확인 팝업의 제목은 `ERPia`다. 기존 로그인 팝업 정규식
(`경고|알림|오류|에러|실패`)에 **걸리지 않는다.** 매출처리 단계에서 별도로 처리한다.

### 4-0. ★ 수집 완료 판정은 15초 한 번으로 끝낸다 (사용자 확정 2026-09-07)

`[가져오기]` 후 **15초** 안에 `매출처리` 버튼이 비활성이 되면 수집이 시작된 것이고,
그렇지 않으면 **이미 끝난 것으로 보고 바로 다음 단계로 간다.** 매출 유무와 무관하다.
(자동수집만 이렇다. 엑셀수집은 파일마다 `wait_upload_settled` — ERPia 가 한가해지는
5초 유휴로 판정한다, 09-08.)

없앤 대기 두 가지 (2026-09-07 실행에서 실측)

| 없앤 것 | 낭비 | 이유 |
|---|---|---|
| 수집로그에 움직임이 있으면 30초 연장 | 31초 | 이 환경에서는 수집 중에도 버튼이 회색이 되지 않는다 |
| 주문 그리드 행 수 안정화 대기(`long_task` 120초) | 121초 | 버튼이 활성 = 수집 종료. 그리드는 이미 최종이다. 0건이면 변화가 없어 120초를 통째로 버렸다 |

→ 수집 구간이 **179초 → 21초**가 됐다.

### 4-3-1. ★ 수집 0건이면 매출처리를 건너뛴다 (사용자 확정 2026-09-04)

조회된 주문이 **0건**이면 이 화면에서 할 일이 없다. 매출처리를 눌러도 확인 팝업이
뜨지 않아 팝업 대기에서 멈춘다.

→ `process_sales()` 는 **`조회된 주문수` 라벨**(`lbl_selectcountno`)이 0 이면 `skipped=True` 로 즉시 돌아온다.
   그리드 행 수로 보지 않는다 — 그룹 행이 섞인다 (3행 = 그룹 1 + 주문 2, 09-29).
   **자동수집·엑셀수집 공통**이며, 흐름은 그대로 물류대기로 넘어간다.

### 4-4. 완료 판정

확정 — 2단 팝업([예] → 결과 [확인], `docs/CONTROLS.md` 매출처리) 을 닫은 뒤 상단
`미매출 주문수` 라벨의 전후 차이를 처리 건수로 쓴다 (`order_mapping.unsold_number`, 09-21).

## Phase 8 — 물류대기 관리

매출처리된 전표 중 **재고가 부족한 건에 배송보류를 걸고, 정상 건만 물류처리로 넘기는** 화면.

근거: 사용자 설명 + 화면 확인 (2026-09-04). 컨트롤 식별자는 `docs/CONTROLS.md` "물류대기" 에 확정돼 있다.

### 작업 순서

```
물류대기 관리 화면 진입 (탭 이름: 물류대기 관리)
  ↓
[상품별 재고검토] 좌측 세로탭
  ↓
[조회(F)]  ← 탭이 바뀔 때 1회만. 보류를 걸어도 재조회하지 않는다
  ↓
┌─ 상단 그리드에서 '부족수량' 값이 있는 행마다 반복 ────────────┐
│  행 선택                                                      │
│    ↓                                                          │
│  하단 그리드(주문정보)에서 같은 ERP상품코드 행을 전부 체크     │
│    ↓                                                          │
│  우클릭 → [배송보류]                                          │
└───────────────────────────────────────────────────────────────┘
  ↓
[일반] 좌측 세로탭
  ↓
[조회(F)]
  ↓
헤더 체크박스로 전체선택
  ↓
[저장(S)]
  ↓
저장 확인: 화면이 재조회되어 체크가 전부 풀린다
  ↓
좌측 프로세스바 [물류처리] → 물류관리 화면 (Phase 9)
```

### 확정된 규칙 (사용자 확인 2026-09-04)

| # | 항목 | 내용 |
|---|---|---|
| 1 | 부족 행 처리 | **부족수량이 있는 모든 행을 하나씩 반복**한다. 한 건만 하는 게 아니다 |
| 2 | 재조회 | 배송보류를 걸어도 상단 목록은 변하지 않는다. **조회는 탭 전환 시 1회만** |
| 3 | 부족 판정 | `부족수량` 이 **비어 있으면 정상**, 값이 있으면 부족 |
| 4 | 조회조건 | 화면 기본값 그대로. 건드리지 않는다 |
| 5 | 저장 확인 | **팝업이 없다.** 체크 상태는 읽을 수 없어(셀 값이 늘 `'선택'`) **일반 탭 행 수가 줄면** 저장된 것으로 본다 (`save_general`). 줄지 않고 ERPia 가 한가하면 '처리할 정상 건 없음' 으로 끝낸다 |
| 6 | 부족 0건 | 배송보류를 건너뛰고 바로 [일반] → 전체선택 → 저장 |

### "파란색 행" 의 정체

사용자 설명은 "파란색으로 처리된 row"지만 **UIA로 배경색은 읽을 수 없다.**

화면을 비교하면 파란 행의 정체가 드러난다.

| 상단에서 선택한 행 | 하단에서 파랗게 표시된 행 |
|---|---|
| 자체코드 `a1`, 상품코드 `8800000000005` (상품A) | ERP상품코드가 전부 `8800000000005` |

→ **파란 행 = 상단 선택 행과 ERP상품코드가 같은 행.**
색이 아니라 이 값으로 매칭한다.

### ★ 하단을 ERP상품코드로 정렬한다 (09-17 — 09-04 "정렬하지 않는다" 를 뒤집음)

`ensure_bottom_sorted` 가 헤더를 눌러 오름차순으로 맞추고(이미 정렬돼 있으면 안 누른다),
정렬이 확인된 경우에만 **대상 코드 묶음이 끝나는 곳에서 스캔을 멈춘다.** 정렬을 확인하지
못했으면 예전처럼 끝까지 훑는다. 근거·실측은 `docs/CONTROLS.md` "하단 정렬" 과 `docs/HANDOFF.md` 09-17.

### 우클릭 메뉴

```
선택영역 체크 / 선택영역 체크해제 / 선택영역 체크 / 선택영역 체크제거
배송보류(주문단위) / 배송보류 / 배송보류해지(주문단위) / 배송보류해지
보류사유 추가 / 매출등록창 열기 / CRM조회창 열기 / 창고 변경 (주문단위) ▸
```

**`배송보류(주문단위)` 와 `배송보류` 가 둘 다 있다.**
부분 일치로 찾으면 엉뚱한 항목을 누른다. **완전 일치로 찾을 것.**

## Phase 9 — 물류관리 (물류처리)

물류대기에서 저장된 전표를 **개별배송으로 등록하고 택배사·박스를 지정해 확정하는** 화면.

근거: 사용자 설명 + 실행 검증 (2026-09-04, 박스 2026-09-07). 컨트롤 식별자는 `docs/CONTROLS.md`.
구현: `automation/logistics.py`

### 작업 순서

```
물류대기 저장 → 좌측 프로세스바 [물류처리]
  ↓
화면이 자동으로 조회 + 등록모드 진입
  (탭이 이미 열려 있으면 안 한다 → [등록(I)] → [주문조회(J)] 로 보완)
  ↓
하단 주문 그리드 전체선택
  = '매출구분' 헤더 **좌측 인디케이터 셀** 클릭 (체크박스 컬럼이 없다)
  ↓
아무 행이나 우클릭 → [개별 배송(B)]
  ↓
전표가 상단 배송등록 그리드로 이동  ← 전체선택 성공 여부는 여기서만 판정된다
  ↓
좌측 배송정보설정 [업체] 드롭다운 → 사용자가 입력한 택배사와 완전 일치 항목 선택
  ↓
[적용] (cmdTag)  ← 상단 그리드 전체에 걸린다. 행을 따로 선택하지 않는다
  ↓
[박스] 드롭다운 → 사용자가 입력한 박스와 완전 일치 항목 선택
  ↓
[적용] (cmdTagAmt)  ← 택배사와 별개 버튼이다. 같은 방식으로 전체에 걸린다
  ↓
[저장(S)]
  ↓
하단 주문 목록에서 전표가 빠지면 완료
```

### 확정된 규칙 (사용자 확인 2026-09-04)

| # | 항목 | 내용 |
|---|---|---|
| 1 | 택배사 | 설정 `delivery_company`(실행 창 [설정]·웹에서 바꾼다). 드롭다운에서 **완전 일치** 항목을 고른다 |
| 2 | 적용 범위 | [적용]은 상단 그리드 **전체**에 걸린다 |
| 3 | 박스 | **택배사와 같은 로직**으로 처리한다 (사용자 확정 2026-09-07). 설정 `delivery_box` 를 `cboTagAmt` 에서 완전 일치로 고르고 `cmdTagAmt` [적용]. 택배사 적용 **다음**, 저장 **앞**이다 |
| 4 | 미설정 적용 | `chkBatchOption` 은 **건드리지 않는다** |
| 5 | 조회조건 | 화면 기본값 그대로 |
| 6 | 저장 전제 | 요금(0 이상) / 연락처1 / 우편번호 / 주소가 채워져야 저장된다 |
| 7 | 저장 팝업 | 정상 데이터에서는 없다. 배송요금 등이 비면 뜬다 |
| 8 | 자동화 범위 | **[저장(S)] → 저장 확인 → [운송장출력] 까지** (사용자 확정 2026-09-10). 저장이 정상이면 팝업 없이 **[등록(I)] 이 활성화**된다. 그때만 `cmdPrint_Tag_Form` 을 누른다. 출력 창은 사람이 처리한다 |
| 9 | 저장 실패 시 | [등록] 이 활성화되지 않으면 **운송장출력을 누르지 않는다.** 실패 알림이 [확인] 하나면 **닫고** 글을 결과에 남긴다 (`dialogs.dismiss_message_box`, 09-22). 다른 버튼이 있으면 두고 경고만 남긴다 |

### 판정에 쓸 수 없는 것

- **행 선택 상태** — `IsSelected` 가 갱신되지 않는다. 항상 `행 1`만 선택으로 보인다
- **상단 그리드 행 수** — 저장 후 재조회되어 **늘어난다**. 완료 지표로 쓰면 안 된다
- **저장 직후의 그리드 읽기** — 모달 팝업이 떠 있으면 UIA 호출이 막혀 멈춘다
- **행 수 = 전표 수** — 상단은 박스(송장 = 배송전표) 한 줄 아래에 상품 줄이 붙는다. 만든 전표 수는
  `배송업체` 가 찬 줄을 저장 직전에 끝까지 센다 (`logistics.count_boxes`). **개별배송은 주문 하나를 박스 여럿으로
  나눌 수 있다** (09-29 실기: 하단 주문 2건 → 송장 31) — 하단 매출번호 수는 올라간 **주문** 수다


## 개별배송으로 올라온 행이 없을 때 (2026-09-10 사용자 확정)

물류관리에서 전체선택 → 우클릭 → [개별 배송(B)] 를 눌렀는데 **상단으로 올라온
행이 없는 것은 오류가 아니다.** 그 매출전표들에 **배송보류가 걸려 있으면**
배송할 수 없어 등록되지 않는다.

그래서 자동화는 이렇게 동작한다.

| 상황 | 동작 |
| --- | --- |
| 등록된 행이 있다 | 택배사·박스 적용 → 저장 → [등록] 활성 확인 → 운송장출력 |
| **등록된 행이 0행** | `등록 대상 없음(배송보류 등)` 으로 로그를 남기고 **정상 종료**. 택배사·박스·저장·운송장출력을 하지 않는다 |
| 저장을 눌렀으나 [등록] 이 살아나지 않는다 | 저장 실패다. 알림이 [확인] 하나면 **[확인] 을 눌러 닫고** 글을 '확인할 것' 에 남긴다 (09-22). 운송장출력은 하지 않는다 |

★ 전체선택이 실제로 됐는지는 **선택된 행 수로 확인한다** (실측 가능하다).
  예전에는 "선택 상태를 읽을 수 없다"고 보고 검증하지 않아서, 등록 0행을
  전부 "전체선택 실패"로 오해하게 만들었다.

★ 상단으로 올라오기를 기다리는 시간은 **20초**(`logistics.REGISTER_TIMEOUT`)다.
  예전에는 `long_task`(2분)를 다 기다린 뒤 예외를 냈다.
